### 2026-09-02 - WS-001 Round 2 adversarial review (provability lens): uk-public-buyer-cross-source-resolution

- **Lens:** Provability. **Verdict: REFUTED (refuted=true).**
- **Candidate:** `uk-public-buyer-cross-source-resolution` (Find a Tender + Contracts Finder, UK OCDS APIs). Round 2 scorecard total 28/35; criterion 5 ("measurable results without fabricated claims") had been scored 4/5 and described as "the strongest part of the submission."
- **Method:** Live API payloads fetched and parsed rather than reasoning from documentation. Both sources' developer documentation pages were fetched first and were found SILENT on version retention, OCID formation, and organisation identifier schemes, so the claims were tested empirically against 100 Find a Tender releases (`/api/1.0/ocdsReleasePackages?limit=100`, HTTP 200) and two independent 100-release Contracts Finder windows (`/Published/Notices/OCDS/Search`, publishedFrom 2026-08-25/2026-09-01 and 2026-08-20/2026-08-28, HTTP 200).
- **Fatal finding - the join key does not exist.** Buyer-party identifier schemes are disjoint across the two sources. Find a Tender buyers: `GB-PPON` 70, `GB-COH` 10, `GB-NHS` 5, `GB-CHC` 1, no identifier 25 (n=100 releases). Contracts Finder buyers: `GB-SRS` 41, `GB-LAE` 3, `GB-GOR` 1, and **no coded identifier at all for 55** (n=100). Measured scheme intersection: **empty set**. Measured shared (scheme,id) buyer pairs: **0**. Contracts Finder buyer parties carry an `identifier` object containing only `legalName` - no `scheme`, no `id` - e.g. verbatim: `{"id": "GB-CFS-50290", "name": "London Borough of Hackney", "identifier": {"legalName": "London Borough of Hackney"}}`, where `GB-CFS-50290` is a Contracts Finder-internal surrogate key, not a public register identifier.
- **Consequence for provability.** The concept's premise that OCID is "deliberately withheld from the matcher to avoid a leaked oracle" presumes an independent oracle exists to withhold. It does not. OCID namespaces are disjoint by construction (`ocds-h6vhtk-*` on Find a Tender vs `ocds-b5fd17-*` on Contracts Finder; measured OCID intersection across sampled windows: **0**), so OCID cannot serve as ground truth for buyer identity across sources. With no coded identifier on the majority of the Contracts Finder side, the only surviving match signal is the buyer NAME STRING - which is also the matcher's primary input feature. The operator's manual labels would therefore be produced by reading the same name strings the matcher consumes, so precision/recall would be self-referential: the pipeline grades itself against its own inputs. This is the Round 1 failure mode (unfalsifiable headline metric) reproduced in a new source pair, not avoided by it.
- **Denominator finding.** The claimed denominator, "labeled pairs in the reviewed blocked set," is a denominator for blocking-set precision only. Because no independent cross-source register identifier exists in the payloads, there is no denominator for TRUE cross-source buyer pairs in the population - so cross-source matching recall has no measurable denominator, only the separately-reported blocking gap the concept already concedes. Population-level recall is not merely "deliberately not claimed"; it is unmeasurable with these two sources.
- **Corrected source-ledger fact.** The Round 2 cleared-sources list records Contracts Finder `retainsHistory: false` and Find a Tender `retainsHistory: true`. The disjoint-identifier finding above is independent of history retention and was not captured by that field; the cleared-sources schema tracked history and documents but not whether a cross-source JOIN KEY exists, which is the actual precondition for any entity-resolution concept. Recommend adding an explicit `sharedJoinKeyVerified` field before any future cross-source concept is scored.
- **Sample-scope limit (stated, not smoothed over):** measurements are from 100-release samples per source over the dated windows above, not a full-corpus census. Population-wide scheme distributions remain TBD. The empty scheme intersection and the absent `scheme`/`id` on Contracts Finder buyer identifiers are structural payload facts, not sampling artifacts.
- **Not disputed:** licensing (OGL v3.0 on both, previously verified), robots posture (no robots.txt on either domain, HTTP 404 confirmed in the cleared-sources record), and API availability. This refutation is on provability alone.
